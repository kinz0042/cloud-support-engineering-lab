# Offline object-access investigation

This exercise is a **toy teaching service**, not Amazon S3, an AWS IAM simulator, a real bucket, or evidence of an AWS investigation. Its HTTP routes, `X-Lab-Principal` header, toy rules and responses are invented. It binds to `127.0.0.1` and serves only in-memory synthetic objects. No AWS account, Docker or cloud resources are needed.

It illustrates a narrow support problem: a client can list a permitted prefix and read one object, yet a specific report is denied. A separate recovered fixture grants only that report; unrelated reports and the private prefix remain denied.

## Start the broken fixture

From the repository root, start the service and keep the terminal open:

```sh
python scripts/s3_access_lab.py --phase broken
```

The default address is `http://127.0.0.1:8095`. On Windows use `py` if needed and `curl.exe` instead of `curl`. If the port is occupied, stop and identify the conflict; alternatively choose a different port with `--port` and adjust the URLs. Do not stop an unfamiliar process.

In a second terminal, send these synthetic requests:

```sh
curl -i http://127.0.0.1:8095/health
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/list?prefix=allowed%2F'
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/get?key=allowed%2Freadme.txt'
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/get?key=reports%2Fsettlement-demo.json'
curl -i -H 'X-Lab-Principal: integration-demo' http://127.0.0.1:8095/v1/policy
```

Expected statuses for the supplied fixture are 200, 200, 200, 403 and 200. Record your actual response status, `X-Request-ID` and time. Compare the last request's toy policy with the report key. In the server terminal, correlate the report request ID with the structured `toy_access_request` event. Logs contain fixed route, status and toy reason, not request headers or raw URLs.

Form alternatives before deciding: wrong principal, missing object, missing toy allow, and an explicit toy deny. The fixture shows one explanation; a real S3 403 alone does not establish the cause. The test principal is a public label, not an AWS credential or authentication method.

## Apply the controlled recovery

Stop the first service with Ctrl+C, then start the **separate local fixture**:

```sh
python scripts/s3_access_lab.py --phase recovered
```

Repeat the report read and the previously successful reference read. Then check these negative controls:

```sh
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/get?key=reports%2Fother-demo.json'
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/get?key=private%2Fpayroll-demo.json'
curl -i -H 'X-Lab-Principal: integration-demo' 'http://127.0.0.1:8095/v1/list?prefix=reports%2F'
```

The intended report and original reference should return 200; the three negative controls should remain 403. Inspect `/v1/policy` again: the recovered toy fixture adds one exact report key. It does not modify Terraform or any AWS policy. Stop the service with Ctrl+C.

## Investigation record and boundaries

Use [INC-010](../../incidents/INC-010/brief.md) and the [incident template](../../incidents/TEMPLATE.md) to record the customer's complaint, affected action and object, observations, alternative hypotheses, request IDs, change, positive and negative validation, customer update, engineering handoff and remaining uncertainty. Mark any assistance. The response and logs are generated by this local program, not AWS CloudTrail or S3.

The toy model has only exact list prefixes, simple get-prefix and exact-key allows, and a prefix deny. It has no AWS Signature Version 4, IAM policy language, bucket policies, organization controls, permissions boundaries, session policies, access points, VPC endpoint policies, ACLs, KMS, cross-account authorization or real S3 semantics. It must never be used to decide or change live access. In particular, real S3 may return 403 for a missing object when the caller lacks the relevant bucket-list permission; this toy's 404 behavior is deliberately not a faithful model of that case. See [AWS GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) and [AWS access-denied troubleshooting](https://docs.aws.amazon.com/AmazonS3/latest/userguide/troubleshoot-403-errors.html).

The provided Terraform module remains an unattached policy and an undeployed bucket scaffold. A real exercise requires an authorized sandbox, a budget and separate live evidence. Do not publish actual credentials, object contents, account IDs or unredacted policy exports.
